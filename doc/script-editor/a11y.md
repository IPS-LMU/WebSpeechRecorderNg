# Accessibility: what is automated, and what a person must do

ui-spec §8 lists the contract. Two of its parts need different tools, and this file is the record of
both: `bin/a11y_audit.mjs` for everything that is a property of the DOM, and the scripts below for
the screen-reader passes that no headless tool can do.

## Automated: `bin/a11y_audit.mjs`

Drives an already-running Chrome over the DevTools Protocol (the same pattern as
`bin/theme_audit.mjs`), so it needs a served application and a headless browser, not a test runner:

```bash
npm run start_editor -- --port 4300
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --remote-debugging-port=9333 --user-data-dir=/tmp/cdp about:blank &
node bin/a11y_audit.mjs --url http://127.0.0.1:4300/project/Demo1/script/1245/edit --viewports 1366x768
```

It checks, per route and viewport:

1. every interactive element resolves an accessible name (text, `aria-label`, `aria-labelledby`); a
   `title` alone does not count for an icon-only control;
2. every form control has a label, and an `aria-invalid` control wires its message through
   `aria-describedby` — never colour alone;
3. `aria-labelledby`/`aria-describedby` point at elements that exist and have text;
4. ids are unique, because a duplicate silently breaks the two above;
5. images carry `alt` unless they are explicitly decorative;
6. nothing focusable sits inside `aria-hidden="true"`;
7. a `role="radiogroup"` marks its children with `aria-checked`, and a `role="tree"` contains
   `treeitem`s carrying `aria-level` (and `aria-expanded` where they have children);
8. tab order never jumps back up within one column;
9. **the browser's own accessibility tree** — what a screen reader is handed — agrees: no node whose
   role requires a name (button, link, textbox, treeitem, …) is nameless, every `treeitem` carries a
   level, a `tree` has `treeitem`s, a `radiogroup` has radios with a checked state, and a live region
   has something to announce.
10. every interactive target is at least 44 px high — ui-spec §8's house rule. A control inside a
   `<label>` is measured as that label (a 20 px checkbox in a 44 px label is fine), a link flowing
   inline in text is exempt (WCAG 2.5.8), and so is a disabled control. This rule was added after an
   audit found four real violations — the toolbar's brand link, its breadcrumb links, the draws
   view's preview toggle and its session-row selectors — none of which any other rule could see.

Rule 9 is a cross-check from the consumer's side: it reads what the engine computes rather than the
attributes this file looks up, so a broken `aria-labelledby` that shadows a visible label — which
the DOM heuristic forgives by falling back to the text — is still caught. Writing it corrected two
rules of the file itself, which is the kind of thing only the browser's view shows: a live region is
announced by its **contents**, not by a name (no `status`/`alert` needs an accessible name), and a
`radiogroup`'s radios may sit below a wrapper rather than directly under it.

CI runs it for the library list, the editor, the preview, the bank browser, the draw-rule state via
`--prepare bin/audit/open-draw-rule.js`, the draws view and the JSON source. It is sensitive in the
way it needs to be: removing one `aria-label` from an icon-only button makes it fail with that
button named.

## Manual: the two screen-reader passes

Run these per the ui-spec §8 rule (*"one pass per milestone from M2"*), on the route named, after a
build; record the build's commit here with the result. VoiceOver on Safari, NVDA on Firefox.

### VoiceOver (Safari) — the editor

1. `/project/Demo1/script` — the list reads rows as a table; each row announces the script name, its
   id, the counts and the status chip. The legend cards read as headings with their sentences.
2. `/project/Demo1/script/1245/edit` — VoiceOver announces the outline as a tree: the script row,
   then each section with *"level 2, 2 of 5"*, expanding with `VO+→` and collapsing with `VO+←`.
   `↓`/`↑` move; the selected row says *"current"*.
3. With a row selected, `Alt+↑`/`Alt+↓` moves it and the reorder is announced (the move buttons carry
   names, the grip is hidden); the delete button announces the target it removes.
4. `/` focuses the filter from anywhere on the route; typing narrows the tree and the ancestors stay.
5. The inspector announces each field with its label, and an invalid itemcode announces the message
   that follows it (not just a red border). The playback fieldset announces the audition control.
6. `/project/Demo1/script/1245/source` — the textarea is announced as a text area; breaking the JSON
   announces the error with its line, and the checks panel announces the severity word before the
   message (`"Error, E02, …"`).
7. `/project/Demo1/script/playback/preview` — the step simulation announces as a radio group with
   checked states; a disabled step says why; the status line is text, so the state is never
   conveyed by the lamps alone.
8. `/project/Demo1/script/bank-draw/bank/g:0:0` — the rule panel announces `count` with the match
   count, and the suspended state says the count is unknown rather than reading as valid.
9. `/project/Demo1/script/bank-draw/draws` — the table announces session, speaker, drawn/recorded and
   status; the detail lists each itemcode with its bank id and whether it was recorded.

### NVDA (Firefox) — the same nine steps

Differences worth watching: NVDA announces `aria-posinset`/`aria-setsize` as *"1 of 5"* more eagerly
than VoiceOver; Firefox exposes the tree's roving `tabindex` as expected. If a step reads
differently, the fix is in the markup, not in this list — keep the two in step.
